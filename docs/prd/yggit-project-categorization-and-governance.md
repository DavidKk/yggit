## 1. 项目背景与用户核心痛点

### 1.1 现状与实际痛点

开发者或架构师在接入大量代码仓库（通常在 20～100+ 个仓库，如多微服务系统、微前端矩阵、跨端插件及本地测试分支工作树）时，通常会通过 Yggit 的文件夹批量发现（Discover & Import）功能一次性导入所有本地仓库。

在实际使用中，存在以下典型痛点：

1. **扁平堆叠与视觉混乱**：
   - 批量导入的仓库默认全部归入同一个预设分组（如「个人项目」或「未分类」）；
   - 在左上角的项目下拉菜单中，60 多个项目在单列中垂直堆叠，用户必须长时间滚动或强依赖输入检索，无法通过业务模块或架构层级快速定位。
2. **人工分类极其繁琐低效**：
   - 用户虽然可以通过 UI 的「新建分组」和「移动项目」进行整理，但面对数十个仓库，手动逐个新建文件夹并依次拖动/下拉转移需要几十次重复操作，极易放弃维护。
3. **业务域混杂与组织熵增**：
   - 堆叠的仓库往往混杂了多种性质不同的代码库：前后端服务、微前端组件库、运维基础设施、本地单次实验性 Worktree 副本等；
   - 缺乏体系化的项目组织规范，导致研发工作台的巡检与跨仓库查看体验下降。

## 2. 核心设计原则与定位

严格延续 Yggit Workdesk 的核心哲学与交互守卫：

1. **程序负责可靠发现，Agent 负责理解与协助**：
   - **不依赖用户主动发起**：工作台通过确定性算法主动监测仓库分组的堆叠度与路径发散度，若发现异常，自动在「研发规范」泳道生成治理任务；
   - **不滥用 AI 猜测事实**：文件路径、Remote 地址、package.json/go.mod 等均为客观事实；Agent 仅在用户唤起时基于事实证据拟定分组建议。
2. **极简交互与双入口协同**：
   - **被动发现入口**：在工作台（Workdesk）看板中以一张规范卡片形式呈现，点击药丸即携带所有上下文；
   - **主动请求入口**：用户在任何时候呼出底部的 Git Agent 药丸，直接输入“帮我把项目分类整理一下”，均可触发同一套智能治理方案。
3. **透明、安全的写操作守卫 (Approval Guard)**：
   - Agent 绝对不私自修改任何项目分组；
   - 必须先输出清晰结构化的**分组方案预览表**（包含拟建组名、归属项目及分类理由）；
   - 用户审查并确认无误后，点击“确认应用”，程序端批量调用本地 API 在 1 秒内安全执行完成。
4. **纯虚拟编排，不破坏磁盘物理结构**：
   - 分组管理完全作用于 Yggit 的项目目录虚拟清单（`GitProjectCatalog`），严禁移动或重命名物理磁盘上的文件目录，确保对本地环境零侵入。

## 5. 详细功能说明

### 5.1 工作台「研发规范」检测规则 (`OrganizationHygieneDetector`)

在确定性检测管线（Deterministic Pipeline）中新增项目组织度检测规则：

- **输入数据**：本地已接入项目的完整清单 `GitProjectView[]`。
- **触发判定（全部满足）**：
  1. 某个非系统受保护分组（例如 `个人项目` 或 `未分类`）中包含的项目数量 $\ge 10$；
  2. 该分组内项目的 `localPath` 或 `httpsUrl` 呈现出 2 个及以上的独立命名空间前缀（例如同时包含 `/sl-backend/` 与 `/sl/`，或者同时包含不同 GitLab 组 / GitHub Org）。
- **输出 Finding 规范**：
  - `kind`: `'custom'`
  - `ruleId`: `'project-organization-hygiene'`
  - `severity`: `'info'`
  - `conclusion`: `'检测到当前分组堆叠了较多仓库（共 {count} 个），涵盖不同业务域，建议按模块分类整理'`
  - `evidence`: 包含堆叠项目 ID 清单、主要路径前缀样本及分类建议。
- **看板卡片聚类**：
  - 聚类归入看板的第 3 列：**「研发规范」(`standard`)**；
  - 卡片名称：`多仓库分组与架构治理巡检`；
  - 图标：`LuFolderTree`；
  - 范围摘要：`{count} 个项目`。

### 5.2 Agent 专属技能 (`project-categorizer` Skill)

为 Yggit Agent Runtime 提供标准化的仓库分类治理技能：

1. **多维特征提取与启发式匹配**：
   - **物理路径前缀**：提取各项目的父级公共目录（如 `/Develop/sl-backend/*` 归入后端，`/Develop/ops/*` 归入运维）；
   - **远端域名与命名空间**：解析 Git Remote URL 中的 group / namespace（如 `git.inshopline.com/shopline/center-1/website/backend/*`）；
   - **技术栈标识**：根据仓库特征识别类型（如包含 `*-api`、`*-bff` 为后端接口，包含 `*-plugin`、`*-library`、`*-editor` 为前端扩展）；
   - **独立工作树判定**：路径包含 `/worktree/` 或为 linked worktree 副本的，独立归组。
2. **结构化分类方案输出**：
   Agent 在会话中输出友好的 Markdown 表格：
   ```markdown
   检测到你的 61 个项目集中在「个人项目」，我已结合目录结构与服务类型为你规划了以下分组方案：

   | 新建分组                     | 包含项目 (部分示例)                                | 分组依据                   |
   | :--------------------------- | :------------------------------------------------- | :------------------------- |
   | 📁 **Shopline / 后端微服务** | `admin`, `admin-bff`, `order-tracking-api`         | 路径 sl-backend 及后端接口 |
   | 📁 **Shopline / 前端与组件** | `Advanced-Component-library`, `custom-code-plugin` | 前端组件库及扩展插件       |
   | 📁 **基础架构与运维工具**    | `yggdrasil`, `screenshot-server`                   | ops 工具链及本地部署服务   |
   | 📁 **开发工作树与实验**      | `test`                                             | 独立 Worktree 临时环境     |

   确认后我将为你自动创建上述文件夹并完成项目归类。
   ```

### 5.3 一键应用与执行闭环

- 用户在 Agent 消息底部可直接点击 **「确认应用」**；
- Agent 调用本地原子驱动批量完成操作：
  - 批量创建所需文件夹：`createFolder(folderName)`；
  - 批量更新项目所属分组：`moveProject(projectId, folderName)`；
- 刷新全局状态：
  - 顶栏项目下拉菜单即刻按新分组树形展开；
  - 工作台轻量重检，该卡片因堆叠解除而自动标记为 `resolved` 并闭环收起；
  - 支持在通知栏展示轻量反馈“已成功整理 61 个项目至 4 个分组”。

## 7. 验收标准与交付清单 (P0)

1. **确定性检测与卡片展示**：
   - 接入 10 个以上同一分组且路径具有分歧的项目时，在工作台「研发规范」泳道准确生成「多仓库分组与架构治理巡检」卡片；
   - 任务详情左侧按项目展示堆叠列表，右侧准确展示各项目物理路径与 Remote 证据。
2. **Agent 上下文联通与方案拟定**：
   - 点击卡片右下角或底部 Git Agent 药丸，Agent 自动获取该卡片的所有项目信息；
   - 能够基于物理路径和 Remote 结构输出易读、结构清晰的 3～5 个新分组规划方案。
3. **安全批量执行与状态刷新**：
   - 用户确认后，毫秒级调用 `createFolder` 和 `moveProject` 完成迁移；
   - 全局顶栏下拉菜单即时反映新分组，工作台重检后卡片顺利关闭；
   - 严禁执行任何磁盘文件系统的删除或物理移动。
